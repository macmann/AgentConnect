# Backup and recovery verification

Run `pnpm recovery:drill` from the repository root after `pnpm local:init`, `pnpm infra:up` and dependency installation. Docker Compose must have the local PostgreSQL and S3 services running. The configured PostgreSQL role needs permission to create/drop databases, install pgvector and read `pg_control_system()`; the S3 credential needs create/delete bucket and object permissions. Use development credentials for this drill.

The command rejects production mode and non-loopback database/storage endpoints. It compares the configured PostgreSQL server identity with the Compose PostgreSQL service before doing any work. It creates uniquely named source/recovery databases and buckets, applies every release migration (currently through 0016), inserts two synthetic tenants with workspace secrets and tenant-prefixed objects, and adds a vector row. It never dumps or restores the configured application database or bucket.

The drill uses real `pg_dump` custom-format and `pg_restore --exit-on-error` tools inside the existing PostgreSQL container. It reads objects through S3, records SHA-256 hashes and wraps the dump/object archive in AES-256-GCM with a separate random recovery key. The bounded archive and its key stay in memory and are discarded after the run. The application `MASTER_KEY` is never included in the archive. This is a verification command, not a persistent backup/export service.

After restoring into the fresh database and bucket, it checks all migration versions, supported pgvector and vector data, tenant rows, object hashes, secret decryption with the configured master key, and composite foreign-key rejection of mixed-tenant references. Corrupted archives, incorrect archive keys, missing/changed objects, wrong master keys and wrong secret contexts must fail verification. It does not contact model providers.

Success prints one JSON report with snapshot time, fixture counts, encrypted archive size, restore/verification duration and total work duration before cleanup. No secret values, SQL errors or object contents are logged. Failures identify the operation stage. Both success and failure attempt cleanup of only resources created by that invocation. Cleanup failure produces a nonzero exit and `cleanupRequired` resource names. An abrupt process/container termination can leave `ac_drill_*` databases or `ac-drill-*` buckets; investigate and remove only the exact resources belonging to that interrupted run. Never use broad deletion against application storage.

The recovery duration is a synthetic local measurement on the same PostgreSQL/S3 services, not a production RTO. There is no scheduled backup or RPO guarantee. This drill does not verify role/grant recovery (`--no-owner --no-acl`), large datasets, incremental backups, object versions, independent infrastructure failure, Temporal control-plane state, Redis, external credentials or a remote key escrow service.

## Production recovery acceptance

Before a production release, provision encrypted PostgreSQL backups plus WAL/PITR retention, object versioning and independent replication/backup, and separately controlled master-key escrow. Keep encryption keys out of backup bundles and audit retrieval. Record the release/schema version and approved recovery point with each backup set. Coordinate database and object snapshots while writes are quiesced, or use a documented consistency protocol; a database dump alone is insufficient.

Restore an actual retained backup into an isolated environment with separate infrastructure credentials and blocked mail/webhook/provider execution. Recover PostgreSQL including required roles/grants, the corresponding object versions and the original master key. Verify tenant data, storage references, vector queries, decryptability and application access before allowing traffic. Measure achieved data loss (RPO) and recovery duration (RTO) against organization-approved targets. Restore Temporal durable state according to the production topology and rebuild ephemeral Redis state. Exercise missing/corrupt object and unavailable-key incidents, document failover/rollback and obtain independent acceptance. The local drill is a prerequisite check, not completion of these production obligations.
