# Agent tools and service connections

**Tools** and **Connections** open on the registered-tool list. Administrators use **Add tools** to open a three-step wizard: choose, configure, review and save. Search and the type filter keep the list compact; each row has Test and an actions menu for editing, disabling, or archiving. Execution traces, MCP servers, and workflow connection administration open separately.

## Add tools

- **Templates:** Brave web search, the built-in financial calculator, GitHub MCP, Context7 documentation MCP, PostgreSQL, and a connection to your own sandboxed code executor. Templates prefill known settings; enter a name and any required key. The code executor template connects an existing sandbox service; API Toolz does not execute arbitrary code in its API process or provision a sandbox.
- **Custom MCP:** choose Streamable HTTP or an installed STDIO profile, provide credentials or reuse a saved connection, then validate. The wizard discovers remote tools and lets you select up to eight capabilities to register together.
- **API / OpenAPI:** paste an OpenAPI 3.0 or 3.1 specification in JSON or YAML. The server extracts operations, typed path/query parameters, required JSON request bodies, and bearer/API-key authentication. Optionally override the server URL. Review supported operations and warnings, select tools, and save.

New credentials remain in browser/server memory during validation. Final saving encrypts the key and creates the connection and selected tools in one transaction, with tenant-scoped audit events. Existing workspace credentials can be selected instead. Keys are never tool arguments. MCP discovery is repeated when saving; a fingerprint rejects capability/schema changes since the review screen. A failed or cancelled setup does not leave a secret, connector, or partial set of tools behind.

Operations that can write/delete data or execute code are marked explicitly. Registration requires a separate acknowledgement for these selected operations. Tools are workspace-only by default; use the access option to allow anonymous published agents. The model planner is instructed to call tools with side effects only for an explicit user request. This is an administrator trust boundary, not a remote side-effect sandbox or a durable human approval workflow. Use reviewed services and minimally privileged credentials.

## Use tools in an agent

In **Agent → Configure → Tools**, attach multiple enabled tools and save the draft. Start a new playground conversation to use that attachment list. At most eight tools can be attached, with a maximum of five sequential calls per answer. Automatic may select no calls, Always requires a valid relevant call, and Disabled keeps attachments without executing them. Usage instructions and agent instructions guide the planner but do not override registry permissions or argument schemas.

The runtime validates the selected tool IDs and typed arguments, executes calls, and provides successful results as untrusted reference data for the response. Tool results cannot grant access, install integrations, or change policy. Public deployments require explicit public access on every tool. Current enabled/access settings are checked again before execution, including existing conversations and published agents. Publication pins attachment IDs and call budgets, not endpoints or tool revisions.

Test a registered tool with arguments matching its displayed JSON schema. Tests execute the operation and can have the same side effects as an agent call. Recent executions include sanitized arguments/results, status, duration, tool revision, error code, and run reference. Tool results are also shown during playground and hosted chats; saved messages remain available in conversation history.

## Runtime setup and supported transports

- Approve exact HTTP service hostnames in `TOOL_ALLOWED_HOSTS`, for example `api.search.brave.com`, `api.githubcopilot.com`, and `mcp.context7.com`. Private development endpoints need an explicit `host:port` in `TOOL_PRIVATE_HOSTS`. These policies remain separate from model and website access. Cloud network egress must also permit the service. Redirects and unapproved/private destinations are refused; proxy and TLS trust are preserved.
- STDIO uses the official MCP SDK and an exact administrator allowlist in `TOOL_STDIO_PROFILES`. Install the executable/server in the deployment image and configure a JSON array, for example `[ { "command": "/usr/local/bin/my-sandbox-mcp", "args": ["--stdio"], "credentialEnv": "SERVICE_API_KEY" } ]`. The UI selects a profile; it cannot submit arbitrary shell commands or change approved arguments. Credentials are passed only through that profile’s declared environment variable. Child processes use a temporary working directory, a restricted environment, inherited proxy/CA settings, bounded protocol messages, and no logged server stderr. Processes close on completion/cancellation. STDIO profiles are trusted installed programs, **not an OS sandbox**; use a container/sandbox wrapper for code executors and enforce resource/network/filesystem limits there. Profiles must be configured consistently on every service executing tools.
- Streamable HTTP MCP supports finite POST JSON/SSE responses and bounded best-effort session termination on the same endpoint. Background GET subscriptions, OAuth discovery/login, legacy SSE, notifications, resumable sessions, and server-directed endpoint changes are unsupported. A bearer token can be supplied manually; API-key headers are configurable. The Context7 template preselects its CONTEXT7_API_KEY header. Resources/prompts are inspectable discovery metadata, not automatically injected into agent context. A disabled connector prevents its tools from running. Runtime rechecks the registered input schema and the operation’s read-only policy before each call.
- OpenAPI imports support GET, POST, PUT, PATCH, and DELETE; simple primitive path/query parameters; JSON bodies; local component references; bearer tokens (including manually obtained OAuth access tokens); and API keys in headers. Remote references, recursive schemas, multipart bodies, header/cookie parameters, query-string credentials, composed authentication, and complex parameter serialization are not imported. Unsupported operations appear as warnings. Formats are treated as annotations; pattern validation and other unsupported schema constructs are rejected. Specifications are bounded to 300 KB, 100 paths, and 50 discovered operations. Agent arguments use `path`, `query`, and `body` groups, preserving types and required fields. Destination and authentication settings remain fixed in the registry; agents cannot provide URLs or credentials.
- Existing fixed HTTP GET tools and PostgreSQL read tools retain their registry API and edit/test support. PostgreSQL uses administrator-approved `TOOL_DATABASE_HOSTS`, fixed table/columns/filters, a dedicated SELECT-only role, bounded parameterized queries in read-only transactions, and verified TLS in production. Arbitrary SQL is unsupported. The financial calculator supports exact arithmetic with evidence checks. Brave search uses strict safe search and bounded results; result links are data, not automatically fetched.

Tool deadlines remain 0.5–15 seconds. Request/results, schemas, MCP discovery, and persisted grounding data are bounded. Credentials and sensitive JSON property names are redacted from results/traces. Remote schemas and results remain untrusted; outputs may still contain business/personal data selected by the administrator. Malformed plans, unknown tools, schema drift, unavailable credentials, revoked permissions, redirects, and timeouts fail explicitly. No malformed-plan fallback executes a tool.

Workflow HTTP connections and explicit MCP Action grants remain under **Connections → Workflow connections**. These deterministic workflow permissions are separate from tools attached to an agent. Live third-party acceptance requires provider credentials and allowed egress; fixture tests do not establish production connectivity.

## Tool planner failures and API logs

`TOOL_PLAN_INVALID` means the model's planning output failed validation before tools ran; it does not mean a tool endpoint is unavailable. The planner requests JSON object mode on OpenAI/compatible endpoints and Gemini, accepts a complete JSON object optionally wrapped in one Markdown JSON fence, and rejects prose, extra keys, unknown IDs, excess calls and invalid arguments. It never extracts arbitrary embedded JSON, substitutes tool names for IDs, or coerces arguments.

A rejected plan gets one new planning attempt, with its validation category and a reminder of the required contract. No tool runs until the entire new plan validates. Initial planning reserves up to 4,096 output tokens; the second attempt up to 8,192, always capped by the agent's configured output limit. Oversized responses fail without a repair request. If an endpoint explicitly rejects `response_format` with HTTP 400 and no output, the second attempt uses the portable JSON prompt without that parameter. Other provider failures and cancellation do not trigger a format-repair request. All completed attempts remain included in usage accounting.

The API emits **Tool planning response rejected** for each rejected attempt and **Tool planning completed** when validation succeeds. Match `runId`, `traceId`, and request ID with **Agent chat failed**. The `toolPlanning` object includes status, reason, attempt/maxAttempts, willRetry, availableTools, maxCalls, actual planner maxOutputTokens, jsonMode, planBytes/planCharacters, jsonStart/fencedJson, invalidCallIndex, schema issueKeywords, input/output usage, outputLimitReached and durationMs. Reasons include `invalid_json`, `invalid_envelope`, `too_many_calls`, `invalid_call_shape`, `unknown_tool`, `invalid_arguments`, `arguments_size`, `arguments_schema`, `plan_size`, `json_mode_unsupported` and `provider_error`. A token-limit flag is evidence from reported usage, not a definitive truncation diagnosis.

Diagnostics are persisted in `agent_runs.context_breakdown.toolPlanning`, including when repair succeeds, and safe attempt events are attached to the Langfuse `tools.planning` span. They contain no raw plans, prompts, argument values, credentials, arbitrary JSON property names or provider error bodies. Existing Langfuse content capture is a separate opt-in setting. Tool-execution traces can be empty when planning is rejected because there was no valid tool call to execute. On a failure, inspect the correlated planner model generations in Langfuse if content capture is enabled, rather than changing tool destinations or domain allowlists.
