# Knowledge and RAG

The knowledge pipeline implements knowledge bases, document upload, manual text, curated Q&A, bounded website crawling, durable ingestion, hosted/custom embeddings, pgvector retrieval, citations, a retrieval playground and knowledge attached to agents.

## Use it

1. Save an embedding-provider key under workspace **Secrets**. OpenAI and Gemini embedding adapters are supported; an approved OpenAI-compatible embedding server may omit a key.
2. Open **Knowledge**, register an embedding model, select its actual dimensions and test the connection. Dimensions are limited to 1–2000 for the current HNSW vector index. OpenAI text-embedding-3 and Gemini requests include the declared output dimensions; compatible models must already return that dimension. Other OpenAI embedding models must use their native dimension.
3. Create a knowledge base with that model and character-based chunk size/overlap. The embedding model, dimension and standard chunk configuration are fixed; create a new base to change them. Optional advanced processing uses its own token target and can be changed for future ingestion or explicit reingestion. This avoids mixing incompatible vectors.
4. Upload a source or add manual text/Q&A. Source status moves through queued, processing and ready. Failures show a sanitized error code and allow reingestion. Only ready sources participate in retrieval.
5. Use **Retrieval playground** to inspect passages, cosine similarities, original query, context-size estimate and latency. Hybrid mode fuses semantic and PostgreSQL full-text candidates using reciprocal rank fusion; vector mode uses cosine distance. Curated Q&A receives a small hybrid tie-break preference.
6. In **Agents**, select knowledge bases, passage count, minimum similarity and retrieval mode. Save, chat, publish and inspect expandable citation passages in playground, conversation history and hosted chat.

Knowledge defaults to internal use. Public deployments require every attached base to explicitly enable public hosted chat access. That setting permits retrieved passages to be shown anonymously. Turning it off blocks subsequent public retrieval. Agents keep their published configuration and can retrieve current ready knowledge or approved knowledge releases. Release pins freeze indexed passages and parent context; source deletion still revokes their availability.

## Sources and parsers

The parser registry supports PDF, DOCX, PPTX, XLSX, CSV, TXT, Markdown, HTML and JSON. TXT must be UTF-8. Markdown headings, PDF pages, slide numbers and sheet identifiers are retained. Standard tables use labelled text/rows. Optional advanced processing adds grouped-header/table segmentation and heuristic PDF coordinate extraction; see the advanced processing section below. HTML drops active script/style/iframe content. Extracted text and generated responses render as text in the UI.

Limits: 10 MB per uploaded file, 2 million extracted characters, 500 chunks per ingestion job, 200 PDF pages/slides, 100 sheets, 30 MB expanded Office archives, and 2000 archive entries. Empty/scanned PDF text fails explicitly unless optional OCR succeeds. OCR requires OCR_ENABLED plus Poppler/Tesseract, supports English and is bounded to 20 scanned pages per document. Image/audio/video extraction and more sophisticated layout reconstruction remain future extensions. XML entity declarations are rejected. Parsing occurs in the separate ingestion worker process; enterprise parser sandboxing and broader malicious-file validation remain hardening work.

Q&A supports create/edit/delete, tags and CSV import/export. CSV columns are `question,answer,tags`; `|` separates tags. Imports validate all rows first and accept at most 100 rows. Storage/transaction failure can leave a partially created import; successful rows remain individually visible. Export escapes spreadsheet formula prefixes. Source reingestion replaces its documents/chunks in one database transaction after all embeddings are ready. Previous chunks are excluded while a source is queued or processing.

## Website ingestion

Single-page and same-origin recursive crawling are supported, defaulting to 20 pages/depth 2, with configurable limits up to 100 pages/depth 5 and allowed/blocked path prefixes. Canonical URLs remain same-origin and preserve source provenance. The crawler respects robots.txt, uses `AgentConnectKnowledge/1.0`, rejects redirects, requires HTML, and caps page/robots response sizes. A robots 404 permits crawling; other HTTP errors fail the job. The built-in Cheerio crawler processes static HTML. Firecrawl can process rendered public HTTPS sites using an encrypted workspace key; its returned pages are scoped and bounded before ingestion. Scheduled crawling is not implemented. Manual reingestion refreshes the source; knowledge connectors have their own synchronization flow.

Website hosts are empty by default. Set exact `KNOWLEDGE_ALLOWED_HOSTS` in the API/worker environment and permit those domains in cloud network settings. Private servers require an explicit `KNOWLEDGE_PRIVATE_HOSTS=host:port` exception, empty by default. Provider traffic separately uses `MODEL_ALLOWED_HOSTS`. HTTPS, private-address rejection, direct DNS pinning, exact destination approval and the inherited cloud proxy constrain requests. Do not broaden access to arbitrary destinations to make a crawl succeed.

## Durable worker and storage

Original inputs and fetched pages use tenant-prefixed private S3-compatible object keys. PostgreSQL stores sources, document revisions/provenance, chunks, embedding spaces and jobs. Each knowledge base has a dimension-specific partial HNSW cosine index; full-text search has a GIN index. Composite foreign keys enforce tenant and embedding-space identity.

The worker runs independent mail, ingestion and object-cleanup loops. Ingestion claims jobs using `FOR UPDATE SKIP LOCKED`, stores a unique lease token, renews a two-minute lease, and stops at a five-minute deadline. Expired leases recover; retryable provider/website failures use persisted backoff with at most three attempts. A transaction checks lease, source revision and archive state before publishing results. Superseded jobs cannot replace a newer source revision.

Deleting sources or archiving a base immediately removes searchable chunks and cancels pending jobs. Durable source tombstones queue all raw source objects for purge after a ten-minute grace period, allowing in-flight jobs to stop. Purge failure leaves the tombstone pending for retry. Old revisions of an active source remain in its object prefix until deletion; configurable retention/version cleanup belongs to the operations phase. This queue is a tested PostgreSQL outbox implementation, not a Temporal ingestion workflow.

## RAG tool and citations

`packages/rag` defines the built-in RagTool interface and source/citation structures. `PostgresRagTool` enforces the workspace/public boundary, embeds queries using the base's fixed model, retrieves ready chunks and assembles bounded passages. Existing agents retrieve before generation whenever knowledge is attached. Configure → Knowledge now supports Automatic (a relevance decision before retrieval), Always (required retrieval), and Disabled (retain attachments without retrieval), with usage instructions. See [usage policy details](agent-runtime.md#tool-and-knowledge-usage-policies).

Reference passages are framed as untrusted data with explicit grounding instructions. SSE sends retrieved sources, then tokens and terminal results. Completed responses must include valid `[n]` references by default; only actually referenced retrieved chunks become persisted/displayed citations. Unknown references and required-but-missing citations fail the run. No relevant passages fail before generation. A citation includes chunk/document/source/base identity, title, available page, canonical URL, passage text and relevance score.

Reference validation does not prove that every generated claim is entailed by its source. A failed streamed answer may already have displayed partial text; the terminal error marks it unsuccessful. Optional query rewriting and LLM reranking are implemented with safe retrieval fallbacks. Advanced ingestion supports token-aware chunks and validated LLM boundary assistance. Retrieval playground token counts remain estimates; agent context controls can use configured tokenizers. Automated claim-level faithfulness checks remain a future extension. Dataset-scale latency/load and recall benchmarks are not yet established.

## Validation

Fixture-backed tests exercise actual PostgreSQL/pgvector, S3 objects, PDF/Office extraction, lease recovery/backoff, dimension rejection, tenancy, robots/redirect restrictions, citation persistence and public access revocation. Browser tests use explicit local HTTP embedding/chat protocol fixtures and the actual compiled ingestion worker. No production mock mode or deterministic embedding fallback exists. Live hosted embedding/generation acceptance remains unverified because provider credentials are absent and the cloud egress changes are a draft.

## Opt-in advanced processing

Knowledge settings expose an advanced processing switch, optional workspace-model assistance and a 100–1500 token target (default 500), independently of the parent-context retrieval switch. Off preserves the standard parser/chunker and makes no processing-model calls. Settings are captured when a job is claimed and persist across retries; existing indexed content is unchanged until manually reingested.

Advanced parsing captures raw table rows, reconstructs HTML spans, expands Excel merged cells and row separators, handles Word horizontal grid spans and groups PDF text by coordinates. Deterministic segmentation retains original values with grouped column labels and nearby unit/title/footnote context. Layout uncertainty is reported rather than hidden. Optional LLM assistance supplies only contiguous indexed row ranges and header counts: strict validation rejects gaps, overlap, extra fields and invalid headers. Requests use the selected workspace model/credential and existing endpoint controls, at most 12 calls per job, 150 rows per request, model-context/output bounds and 20-second deadlines. Provider errors and rejected plans fall back to deterministic processing with visible warnings. Cancellation propagates through the ingestion deadline.

Advanced chunks use o200k token counts and retain complete table rows. Wide rows may exceed the target; a row above 8,192 tokens fails explicitly. Narrative substrings preserve exact Unicode/text. Parent context includes bounded neighboring chunks from the same section/table/page, normally up to 1,500 tokens; the matched child remains intact when larger. Expansion is separately opt-in, consumes existing agent context budgets and never makes an additional LLM call. Approved releases copy chunk metadata so current-source reingestion cannot change their parent evidence. Old standard chunks/releases simply do not expand.

Extraction previews are read-authorized and scoped to the source's current revision. They show up to 100 table samples per document, up to 6,000 characters each, warning messages and provider-reported LLM usage. Sources flag processing-setting changes that require reingestion. Previewing does not approve or publish content automatically.

Financial extraction remains heuristic: vertical Word merges, irregular PDF layouts and scanned tables need review. Excel display styles are not reconstructed and formulas are not recalculated. There is no structured financial-fact store or deterministic financial calculation engine in this change. See [the user guide](user-guide.md#advanced-document-processing-and-financial-tables).

## Knowledge planning resilience

Knowledge usage reuses `rag.usageMode`: Automatic (`automatic`), Always retrieve (`always`), and Never retrieve (`disabled`). Existing configurations retain their previous default of Always. Grounded answer policies continue to require Always and approved knowledge; their UI does not offer incompatible usage modes.

Automatic planning uses the minimal strict `{ "retrieve": boolean }` schema. Query rewriting remains a separate, optional retrieval stage rather than adding a duplicate planner query. OpenAI and Gemini requests carry native JSON-schema constraints; compatible providers and Anthropic use the same prompt and portable parsing. Whitespace, markdown fences and harmless surrounding prose are accepted around exactly one object. Arrays, extra keys, non-booleans, duplicate keys and ambiguous objects are rejected.

A syntactically or schema-invalid response gets exactly one bounded repair call. If that also fails, the customer request proceeds to normal retrieval using the original user message. The usual query rewrite, hybrid fusion, thresholds, selection limits and citation rules still apply. Attachment authorization, tenant/public boundaries, missing sources, unavailable releases, provider transport/authentication failures and cancellation remain authoritative failures; formatting fallback does not synthesize evidence.

`agent_runs.context_breakdown.retrievalEnhancements` records planning status, attempts, query source (`planner`, `repair`, `raw_query_fallback`, `always_retrieve` or `disabled`), provider/model identity, rewrite/rerank outcomes and selected chunk count. Fallback emits a structured terminal warning with run/trace identity and `KNOWLEDGE_PLAN_INVALID`, without user messages, planner output, credentials or source content. OpenTelemetry adds knowledge planning, query rewrite, embedding, retrieval, ranking/fusion and reranking spans; the existing agent run/provider-call traces cover generation. Repair usage is included in model usage and quota accounting.

For a dedicated password-recovery assistant, choose Always retrieve, hybrid search and required citations. This skips the relevance-planning call; source quality and answer faithfulness still need review against the approved password-recovery procedure.

Website registration errors now identify the exact rejected hostname and required API/worker configuration. `KNOWLEDGE_ALLOWED_HOSTS=www.yomabank.com` allows `https://www.yomabank.com/`, but not `https://yomabank.com/`. Environment values are loaded when services start; restart both API and worker after edits, and check inherited environment overrides if the running API still rejects the host. Rejected submissions emit `Website crawl request rejected` with safe codes, hostname, configured-host count, approval status and invalid field paths; no credentials, query strings or request bodies are logged.

The built-in crawler follows up to five redirects within the original origin. It checks endpoint approval and pins/validates DNS on every hop, obeys robots.txt and path filters before fetching redirected pages, resolves relative links against the landing-page URL, and retains redirect provenance. Cross-origin/credential-bearing redirects remain blocked; loops and excessive chains fail with `WEBSITE_REDIRECT_LIMIT`. Use the direct landing URL if a site redirects to another origin, and explicitly approve that host. URL whitespace is normalized and HTTP(S)/credential/path settings are validated before browser submission.
